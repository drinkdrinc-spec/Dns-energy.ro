# RCA — dns-energy publish fails ("DE CE NU SE PUBLICA?")

## Summary
The deploy is **not failing at build** — the image builds fine. It fails at the **deploy_k8s** step because the **backend crashes on every boot**, so the new pods never become Ready and the rollout times out. The app is therefore never promoted/published.

- Deployment: `dns-energy` (`298c2330-94d7-42a5-bc7e-93acf0357315`)
- Failed run: `1244efe6-af76-459a-9073-ecdd74026dc3` (type: initial)
- Failed step: `deploy_k8s` → "deployment failed to become ready: timed out waiting for the condition"
- Frontend: kubernetes · Template: `fastapi_vite_shadcn_base_image` · Tier: tier_0 · Arch: arm64

## Root cause (proven)
On startup, `server.py` (line 523) imports `docgen.py`. At **module-import time** `docgen.py` registers TrueType fonts:

```
backend/docgen.py:18  FD = "/usr/share/fonts/truetype/liberation/"
backend/docgen.py:19  pdfmetrics.registerFont(TTFont("LS",  FD + "LiberationSans-Regular.ttf"))
backend/docgen.py:20  pdfmetrics.registerFont(TTFont("LSB", FD + "LiberationSans-Bold.ttf"))
```

The production **runtime base image does not contain the Liberation fonts** — that directory does not exist. reportlab therefore throws and the process dies immediately:

```
reportlab.pdfbase.ttfonts.TTFError: Can't open file "/usr/share/fonts/truetype/liberation/LiberationSans-Regular.ttf"
OSError: Cannot open resource '/usr/share/fonts/truetype/liberation/LiberationSans-Regular.ttf'
...
Backend died, shutting down nginx...
nginx: connect() failed (111: Connection refused) ... GET /health -> 127.0.0.1:8001
```

Because the backend exits on boot, entrypoint shuts nginx down, `/health` returns connection-refused, readiness never goes green, and `deploy_k8s` times out → nothing is promoted.

### Why it works in preview but not in production
The preview/dev container happens to have fonts installed; the slim production runtime base image does not. SYSTEM/custom secrets are **not** involved — the crash is purely the missing font files. The process gets *past* all other imports (emergentintegrations/EMERGENT_LLM_KEY, pymupdf, pypdf, python-docx, Stripe) and dies specifically at the reportlab font registration, so those are **not** the blocker.

## Evidence / reproduction (eph sandbox, run source)
1. `ls /usr/share/fonts/truetype/liberation/` → **No such file or directory** (only dejavu/droid/noto present). Confirms the font path is absent in the base image.
2. `apt-get install -y --no-install-recommends fonts-liberation` → installs exactly `LiberationSans-Regular.ttf` and `LiberationSans-Bold.ttf` at `/usr/share/fonts/truetype/liberation/` (the exact path+filenames docgen requests).
3. `pdfmetrics.registerFont(TTFont('LS', .../LiberationSans-Regular.ttf))` + `-Bold` with reportlab installed → **"FONT REGISTRATION OK"**. The production traceback is reproduced and the fix is verified.

## What needs fixing
The runtime image must provide the Liberation fonts, OR the app must stop depending on an absent OS font. Either resolves it:

### Option A — Deployment manifest (recommended; already authored/staged)
Install `fonts-liberation` in the runtime image. I have already written this into the deployment's manifest set in GCS (added an apt layer in the `final-base` runtime stage of `Dockerfile.cloudbuild` and the final stage of `Dockerfile`):
```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends fonts-liberation && rm -rf /var/lib/apt/lists/*
```
A pending run (`16d4665b-fe04-44df-91ef-eec590f51b0f`) is staged. **Per instruction, no redeploy was triggered.** One redeploy will adopt the pending manifest and should go green.

### Option B — Code fix (E1), if you prefer not to depend on the OS package
Bundle the two TTFs in the repo (e.g. `backend/fonts/LiberationSans-Regular.ttf`, `-Bold.ttf`) and point `docgen.py`'s `FD` at that in-repo path, so font availability no longer depends on the base image. (Optionally register fonts lazily inside the PDF functions instead of at import, so a missing font can never crash app boot.)

## Not the cause (checked)
- Not a build failure — image built successfully.
- Not secrets/env, not tier/OOM (tier_0, no OOMKilled/137 — it was a clean crash-on-import), not DNS/domain.
